A deployable Ferrite application declares one Cargo dependency, `ferrite-app`,
and the platform source gate rejects any other entry in `[dependencies]`,
including local path dependencies. Shared functionality therefore ships as Rust
source instead of Cargo crates: `ferrite add` copies a package's source tree
into your app's `src/` directory, where it compiles inside your crate, runs
with your app's handles and no others, and passes the same source gate as code
you wrote. See [the one-dependency rule](/kb/guide/one-dependency-rule-explained/)
for why this boundary exists.

## Add a package

Run `ferrite add` from your app directory (or pass `--dir`), then declare the
printed modules at your crate root:

```bash
ferrite add mcp
```

```rust filename="src/lib.rs"
pub mod crypto;
pub mod mcp;
```

The CLI runs six steps in order and writes nothing to disk unless every step
succeeds:

1. It loads the package index from `https://packages.<base>/registry.json`,
   where `<base>` comes from your active MCP login (`https://mcp.<base>/mcp`),
   so each app installs from its active installation's registry. Before signing
   in, `ferrite add` exits with
   `Select a Ferrite instance first or pass --registry`; pass
   `--registry https://packages.ferrite.cloud/registry.json` to target Ferrite
   Cloud directly. Use `--registry <url>` for another remote index, or
   `--path <dir>` for a local checkout containing `packages/registry.json`. The
   CLI caches the index in its config directory so an offline run still
   resolves from the last seen index and reports its age (fetching package
   files still requires network access). Any index whose serial is lower than
   one already seen is rejected as a downgrade.

   For URL indexes, the CLI verifies the detached Ed25519 signature at
   `registry.json.sig`. `packages.ferrite.cloud` and other Ferrite installation
   package hosts are checked against the public key compiled into the CLI. For
   any other registry, pass its trusted public keys in
   `FERRITE_REGISTRY_KEYS=ed25519:<base64>[,...]`. Unsigned indexes and
   untrusted signers are rejected. When no key is trusted for a third-party
   registry, `--allow-unsigned-registry` installs on file digests alone and
   prints a notice; once a key is trusted for that registry, the flag has no
   effect. A failed signature check is always rejected. Local `--path`
   checkouts skip signature verification.
2. It resolves the requested package and its transitive dependencies. Running
   `ferrite add mcp` also installs `sha256-hmac`, which is why the crate root
   above declares both `crypto` and `mcp`.
3. It downloads each listed file and checks it against the SHA-256 digest in
   the index. One mismatched byte aborts the entire install.
4. It maps each file under `src/<mount>/`, using the package's declared root
   unless `ferrite-packages.json` already specifies another (for example,
   `sha256-hmac` mounts under `src/crypto/`). Each `.rs` file receives a
   `@generated by ferrite-pkg` header with its package name and version, and
   inline `#[cfg(test)] mod name { ... }` blocks are stripped because they test
   package internals. Separate test files shipped by a package (`auth`,
   `ferrite-sso`, `preview-gate`, and `agent-sdk`) stay installed and run under
   `ferrite test`.
5. It refuses to overwrite any existing file whose contents differ and lists
   the conflicting paths, unless you pass `--force`.
6. It writes all files, records the requested package's mount in
   `ferrite-packages.json`, and prints the crate-root lines you need: the
   `pub mod` declarations, plus `extern crate alloc;` for packages written
   against `alloc::` paths (`wasm-runtime`, `qjs-engine`, and `serde-codec`).
   Any package that declares Cargo features also outputs a `[features]` block
   (none in the current registry does). After `ferrite add auth`, the CLI also
   prints the sign-in setup, including the secrets `auth` reads along with your
   app's public origin and OAuth callback URLs so you can configure them before
   your first deploy.

`ferrite add` runs on Linux and macOS; on other operating systems it stops
before reading or writing anything.

Treat vendored files as generated source. Do not edit files carrying the
`@generated by ferrite-pkg` header: the next `ferrite add` flags edits as
conflicts, and `ferrite add --force <name>` replaces them. To upgrade to a
newer version, run `ferrite add --force <name>`.

## Use a package without a shell

An agent connected only to the Ferrite MCP server, with no shell to run
`ferrite add`, can inspect and include packages through MCP where the platform
serves those tools. Ferrite Cloud serves all three capabilities; on another
installation, check `tools/list` for `list_packages` and `read_package`, and
check the `deploy_source` schema for a `packages` property.

- `list_packages` lists published packages; passing `query` filters to packages
  whose name, summary, or guide contains every word.
- `read_package {"name": "<name>"}` returns the package guide, its files as
  installed in your app, its dependencies in install order, and the required
  crate-root lines. Guides longer than 24,000 bytes are truncated with
  instructions for reading the rest. Passing `file` returns one file in chunks
  of up to 60,000 bytes; send the returned `next_offset` back as `offset` to
  continue. For `auth`, the setup guide points to `app_host` so you have your
  app's origin and OAuth callbacks before the first deploy.
- Pass package names in the `packages` argument of `code_gate`, `deploy_source`,
  or `rcs_commit`:

```json
{
  "spec": "<the InfraSpec JSON>",
  "files": {
    "Cargo.toml": "...",
    "src/main.rs": "pub mod crypto;\n..."
  },
  "packages": ["sha256-hmac"]
}
```

Before the gate or build reads `files`, the server injects each named package
and its dependencies under `src/<root>/`, byte-for-byte identical to
`ferrite add`, so your request sends only your own files. If you also send a
package file in `files`, the server accepts an exact match and rejects any
difference. Pin a specific release with `"name@version"`; versions the server
does not carry are rejected. If your files plus the requested packages exceed
the MCP request body budget, the call fails and you need to name fewer
packages. The reply lists the injected packages beside the verdict on
`code_gate` and inside `BuildStarted` on `deploy_source`.

On an installation without these MCP tools, you can bundle a package yourself:
read `https://packages.<base>/registry.json` for each package's `root`,
dependencies, and file SHA-256 digests, download each file from
`https://packages.<base>/<package>/src/<path>`, verify every digest, place the
package and its dependencies under `src/<root>/`, and include them in `files`.
Whenever a shell is available, `ferrite add` is simpler because it checks
signatures, adds provenance headers, and prints the crate-root lines.

Running `ferrite add ferrite-auth` fails with a message pointing to `auth`.
Ferrite Core has no platform-managed sign-in service; application sign-in comes
from the `auth` package.

## Security shape

A package has no deployment, bindings, credentials, or resources of its own.
Everything it does at runtime runs through the handles your `ferrite.json`
grants the host app, which is why provider packages such as `auth` and
`messaging` require you to declare egress destinations and secrets yourself.
When a subsystem needs its own failure, scaling, or authority boundary, deploy
it as a separate Ferrite app instead of vendoring a package.

Because vendored source compiles into your crate, its code shares every handle
your application holds. It can read any secret injected into the app and call
any destination declared in `ferrite.json`, beyond the ones its guide asks
for. A secret is set once and is never returned by a read; the running
application receives its value and can call out only to declared destinations.
Read a package's files before adding it, the same way you review code you wrote.
See [What this does not stop](/developers/secrets-egress/#what-this-does-not-stop)
for what code holding a secret can still do with it.
